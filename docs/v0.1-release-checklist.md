# v0.1 release checklist

Target release: `v0.1.0`  
Status: release-candidate checklist after Issue #16 hardening  
Related issues: [#5](https://github.com/yo4e/WorldSimSeed/issues/5), [#16](https://github.com/yo4e/WorldSimSeed/issues/16)

## Runtime and security

- [x] Threat model and trust boundaries are documented.
- [x] Untrusted world specs are the default security assumption.
- [x] Resource-limit categories and ownership are defined.
- [x] Conservative finite numeric defaults are selected from recorded Node/Chromium benchmark evidence.
- [x] Runtime enforces agent, step, batch-run, event, and retained-trace limits.
- [x] Browser host can cooperatively abort a Worker run and later resume it deterministically.
- [x] Limit termination returns a typed `RESOURCE_LIMIT` error with safe structured details.
- [x] Prototype/property escape negative tests exist.
- [x] Unsupported-operation and malformed-spec negative tests exist.
- [x] There is no spec-driven network/filesystem/import path.
- [x] Browser execution uses a Worker and chunk yielding; CI verifies main-thread responsiveness during a representative run.
- [x] Remaining wall-clock/output-byte limitations are explicitly documented rather than implied away.

- [x] Provenance timestamp policy is explicit: host metadata may carry timestamps outside the deterministic engine manifest.

- [x] Browser Worker and headless execution agree on the deterministic acceptance fixture in Chromium CI.

## Remaining release blockers after Issue #16

These are intentionally **not** completed by the hardening work:

- final review/merge of the hardening PR,
- convert the current `[Unreleased]` changelog into final `v0.1.0` release notes,
- change package/engine version metadata from `0.1.0-dev.0` to `0.1.0`,
- keep `private: true` until npm publication is explicitly chosen; if publishing, remove that guard only on the exact tested release candidate,
- run the full gate on the exact release/tag candidate revision,
- verify examples/docs against that exact candidate,
- prepare final GitHub release notes,
- only then create the `v0.1.0` tag / GitHub Release and decide whether/when to publish npm.

## Release mechanics

- [ ] `CHANGELOG.md` contains finalized **versioned** `v0.1.0` release notes.
- [ ] Version metadata is set to `0.1.0`.
- [ ] If npm publication is desired, `private` is deliberately changed only on the tested release candidate.
- [ ] Release commit/tag points to the exact tested revision.
- [ ] Clean install/test is repeated from the exact tag candidate.
- [ ] Examples/docs are verified against the exact tag candidate.
- [ ] GitHub release notes link to docs, examples, security policy, public API, and known limitations.
- [ ] Only after all required gates pass, create the `v0.1.0` tag / GitHub Release.
- [ ] npm publication, if desired, is an explicit separate release action rather than a side effect of CI.

No npm publish, `v0.1.0` tag, or GitHub Release is performed as part of Issue #16.
